DNS64 Browser Extension – Dokumentation

Funktionsumfang, Architektur, genutzte API-Endpunkte, Sicherheit, Testprotokoll und Lizenzen – die technische Beschreibung der Erweiterung.

Chromium-/Brave-Erweiterung (Manifest V3) für Node64: Blocklisten des DNS64-Moduls schalten, die aktuelle Domain freigeben oder sperren – ohne die Weboberfläche zu öffnen. Vorbild ist die Pi-hole-Browser-Erweiterung, umgesetzt gegen die offizielle lokale API von Node64.

  • Stand: 1.4.0 (07.11.2026)
  • Getestet mit Chromium 155 und Brave 156, Node64 1.34.0 (DNS64-Modul 1.34.0), API 1.2.0
  • Kein externer Dienst, keine Telemetrie, keine Fremd-Hosts: alles läuft zwischen Browser und der eingetragenen Node.

Tastenkürzel im Popup: T Blockieren umschalten, A erlauben, D sperren. Eingabefelder sind ausgenommen, damit Tippen nichts auslöst.

Entwicklerhilfe: popup.html?site=example.com zeigt das Popup mit fester Domain statt der des aktiven Tabs.

Einrichtung

Zahnrad → Node-Adresse + API-Key (aus Einstellungen › API-Keys), „Verbindung testen". Beim ersten Start führt das Popup selbst durch die Einrichtung: beide Felder leer, das Beispiel steht nur als Platzhalter darin.

Der Key liegt ausschließlich in chrome.storage.local dieser Erweiterung – nicht im Sync, nicht im Code, nicht im Paket.

2. Architektur

popup.html ──> popup.js ──┐
                           ├─> theme.js   (Hell/Dunkel, gemeinsame Palette theme.css)
options.html ─> options.js ┘

background.js (Service Worker)  – Abzeichen am Symbol, 1-Minuten-Alarm
  • Kein Content-Script. Die Erweiterung liest keine Webseiten. Vom aktiven Tab wird nur der Hostname gelesen (activeTab), damit die Domain-Karte weiß, worum es geht.
  • Kein Remote-Code, kein eval, keine dynamischen innerHTML-Zuweisungen. Symbole stehen statisch im HTML, Text wird über textContent gesetzt.
  • ES-Module für die Seiten (<script type="module">); der Service Worker ist klassisch (Vorgabe von MV3).
  • Alle Netzwerkaufrufe gehen an eine Adresse: die eingetragene Node (http://… oder https://…), Pfad /api/…, Header Authorization: Bearer node64_….

3. API-Nutzung

Alle zwölf im Code verwendeten Endpunkte sind in der API-Referenz der Node beschrieben – HTML unter /api/docs, maschinenlesbar unter /api/openapi.json (API 1.2.0). Geprüft mit einem Skript, das die api('…')-Aufrufe aus dem Quelltext zieht und gegen /api/openapi.json hält – inklusive Feldtypen der Antworten.

Methode Pfad Anfrage gelesene Antwortfelder
GET /dns64/status – version, listen, blocking.{paused, until_resumed, paused_until}
GET /dns64/summary?range=24h – summary.{total, blocked, cached, clients}, blocklistSize, listsLoadedAt
GET /dns64/log?limit=100&q=<name> – rows[].{t, domain, status, reason, rcode}, total
GET /dns64/allowlist – [].{domain, addedAt}
POST /dns64/allowlist {domain} domain (normalisiert)
DELETE /dns64/allowlist?domain= – 204
GET /dns64/denylist – [].{domain, addedAt}
POST /dns64/denylist {domain} domain; 400 = ungültiger Name, 503 = Sperrliste nicht geladen
DELETE /dns64/denylist?domain= – 204
GET /dns64/records – [].{name, type, value} (nur für die Anzeige „lokaler Eintrag")
POST /dns64/pause {minutes: 0…1440} paused, until_resumed, paused_until
POST /dns64/resume {} dieselben Felder

Anmerkungen zur Konformität:

  • minutes: 0 ist laut Schema erlaubt (minimum: 0) und bedeutet „bis zum Wiedereinschalten".
  • Freigabe und eigene Sperre schließen sich serverseitig aus („Eine gleiche Freigabe fällt dabei weg") – die Erweiterung nutzt das, statt selbst aufzuräumen.
  • Fehlerantworten werden angezeigt, wie die Node sie liefert: 401 → „API-Key ungültig", 404 → „Modul aus?", 503 → Text der Node (z. B. „Sperrliste nicht geladen"), 429 → Hinweis.
  • Statusabfragen sind billig; der Service Worker fragt nur /dns64/status (1×/Minute für das Abzeichen), das Popup zusätzlich die Kennzahlen (alle 20 s, solange es offen ist).

4. Wie der Status der aktiven Seite entsteht

DNS64 hat keinen Endpunkt „ist Domain X gesperrt?". Die Erweiterung prüft deshalb in dieser Reihenfolge:

  1. Eigene Sperrliste (/dns64/denylist, gilt samt Subdomains) → „Von dir gesperrt".
  2. Freigabeliste (/dns64/allowlist, gilt samt Subdomains) → „Freigegeben".
  3. Abfrage-Log der Domain (exakt), sonst der Elterndomain: blocked → „Blockiert · ", custom → „Lokaler Eintrag", error → „nicht auflösbar", sonst „Nicht blockiert".
  4. Nichts gefunden → „Noch keine Abfrage im Log".

Zwei Feinheiten, die aus Messungen stammen:

  • Ein Log-Treffer mit reason: own:<domain> zählt nur, wenn der Name noch in der Denylist steht. Sonst zeigt die Karte nach dem Aufheben eine Sperre an, die es nicht mehr gibt.
  • Blockgründe werden lesbar gemacht (group:… → „Gerätegruppe …", cat:… → „Kategorie …").

Genauigkeit: Das Log reicht retention_days zurück (Standard 7 Tage). Für jede besuchte Seite existiert ein Eintrag, weil der Browser sie auflösen musste. Eine Domain, die noch nie aufgelöst wurde, gilt als unbekannt – freigeben und sperren geht trotzdem.

5. Sicherheit

Berechtigungen und ihre Begründung

Berechtigung Wozu
storage Node-Adresse, API-Key, Hell/Dunkel, 401-Zeitstempel
alarms 1-Minuten-Takt für das Abzeichen (⏸/ON/OFF/!)
activeTab Hostname des aktiven Tabs für die Domain-Karte; Zugriff nur nach Klick auf das Symbol
host_permissions: http://*/*, https://*/* Die Node-Adresse ist frei wählbar (IP, Name, Port, HTTP oder HTTPS), deshalb weit gefasst. Anfragen gehen ausschließlich an die eingetragene Adresse; es gibt keine Liste von Fremdhosts. Wer das enger will, kann im Manifest optional_host_permissions mit dem konkreten Ursprung verwenden und die Freigabe beim Speichern anfordern.

Kein tabs, kein scripting, kein webRequest, kein cookies, kein management.

Umgang mit dem API-Key

  • Nur chrome.storage.local (profilgebunden, nicht synchronisiert), type="password" im Feld.
  • Kein Key im Repository, im Paket oder in Logs.
  • Rücksicht auf die Ratengrenze der Node: Nach fünf ungültigen Keys sperrt die Node die ganze Quell-IP (429, danach ein Versuch je 30 s). Ein veralteter Key im Speicher würde also auch den neu eingetragenen blockieren. Deshalb: Statusabfrage einzeln und zuerst, bei 401 alle Timer stoppen, im Service Worker 15 Minuten Pause, und beim Ändern von Adresse/Key wird die Sperre sofort aufgehoben. Gemessen: ein Popup-Öffnen mit falschem Key kostet einen Request statt fünf.

Weitere Punkte

  • Keine dynamischen HTML-Zuweisungen (kein innerHTML mit Variablen), keine Inline-Skripte, keine eval-Familie – geprüft durch eslint-plugin-no-unsanitized und addons-linter.
  • MV3-CSP bleibt unverändert (script-src 'self'); es werden keine CSP-Ausnahmen gebraucht.
  • Schreibende Aktionen sind auf vier Dinge beschränkt: Pause/Fortsetzen, Freigabe an/aus, eigene Sperre an/aus. Nichts anderes wird je gesendet.
  • Oberfläche ist deutschsprachig, Zahlen in de-DE-Formatierung.

6. Hell/Dunkel

  • Quelle ist matchMedia('(prefers-color-scheme: dark)') in der Seite – in Chromium ist das die Einstellung Einstellungen → Darstellung → Modus (gemessen: color_scheme2 1 = hell, 2 = dunkel, 0 = Gerät/System).
  • Der Knopf speichert relativ (themeInverted), wirksam dunkel = systemDark !== inverted. Damit folgt die Anzeige nach dem Umkehren weiter dem System; die Akzentfarbe am Knopf zeigt „manuell".
  • Drei Trigger, weil ein einzelner nicht reicht: change der MediaQuery, ein Abgleich alle 1,5 s (idempotent) und focus/visibilitychange. Messung in Chromium 155: nach einem echten Theme-Wechsel bei geöffneter Seite war matchMedia.matches bereits true, die Oberfläche aber unverändert – das change-Event kommt in Erweiterungsseiten nicht zuverlässig an. Mit dem Abgleich zieht die Anzeige innerhalb von 2 s nach.

9. Bauen und Ausliefern

~/git/dns64-switch-build.sh                # erzeugt ~/git/dns64-switch.crx (~100 KB)
  • Das Skript packt ohne docs/, *.pem, *.crx und ohne sich selbst.
  • Signiert wird mit ~/git/dns64-switch.pem → ID afeiagkmnfjohhngcmpkolbgjgelilai. Der Schlüssel darf nicht verloren gehen: eine neue ID bedeutet Neuinstallation und leeren Speicher (API-Key neu eintragen).
  • Verteilung im eigenen Store auf dem NAS: http://<nas>:8115 (CRX ablegen, Store scannt bei jedem Request) und https://<nas>:8443 für den Klick-Weg; update.xml meldet die höchste Version je ID.
  • Alternativ „Entpackte Erweiterung laden" in chromium://extensions (Entwicklermodus).

10. Bewusste Grenzen

  • Pausen sind nodeweit und mindestens eine Minute. Kein Sub-Minuten-Wert (Pi-hole kann 10 s), keine Freigabe „nur für 10 Minuten" je Domain – dafür fehlt der Endpunkt.
  • Keine Gerätegruppen. DNS64-Gruppen (Kinder, Gäste, Zeitpläne, hold) haben eigene Regeln; die Erweiterung fasst sie nicht an, um nicht versehentlich Familienregeln zu ändern.
  • Keine Ziel-IP-Sperren. DNS kennt nur Namen; IP-Sperren gibt es nur in PROXY64 bzw. in der Firewall (OPNsense).
  • Status aus dem Log statt aus einer Live-Abfrage: eine nie aufgelöste Domain gilt als unbekannt.
  • Nur DNS64 wird bedient (keine Healthchecks, kein DynDNS, kein PROXY64).
  • Der API-Key ist ein Vollzugriffsschlüssel der Node; die Erweiterung braucht keine feineren Rechte, weil die API keine kennt.
